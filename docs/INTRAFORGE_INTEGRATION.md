# IntraForge integration

This document is integration-planning only. IntraForge Core was not inspected
or modified. No API paths or physical table names are assumed; the table
below is a mapping intent, not an implemented contract.

## Adapter contract notes

`src/integrations/intraforge` is the only future _platform_ integration
boundary — it replaces this application's persistence and identity, not its
catalogue data. Catalogue _source_ providers (CSV today; Nengun and any
future TecDoc/manufacturer/supplier feed) live separately under
`src/integrations/catalogues/<provider>/` and implement
`CatalogueProvider`/`FeedProvider` from `src/catalogue/providers.ts`,
independent of whichever platform ultimately hosts the application. See
[NENGUN_FIELD_MAP.md](catalogues/NENGUN_FIELD_MAP.md) for that boundary's
field-level mapping.

Reads come from a stable subscribed snapshot; mutations support either void
(local demo) or `Promise<void>` (future remote commands). A remote adapter
should await its API command, refresh or reconcile the cached snapshot and
notify subscribers. UI commands await completion and surface rejected
promises. Do not implement platform commands as untracked fire-and-forget
requests.

The integration must map errors including validation, not found, permission
denied, conflict and network failure into clear user-facing messages.
Authenticated platform identity and the definitive permission provider
replace the demo persona (`x-demo-role`, which is a simulation only).
Platform-backed inventory commands must be transactional and idempotent.

`src/catalogue/client.ts` is the local reference HTTP adapter.
`CatalogueProvider` is the replaceable paged query contract.
`src/catalogue/repository.ts` owns development reference data and import
invariants. `src/integrations/intraforge/contract.ts` remains endpoint-free:
it defines `IntraForgeContext` (AppInstance id, permission provider) and
`IntraForgeAdapterFactory`, nothing else.

Integration requires paged part/vehicle/category/diagram queries, exact
normalized-number indexes, relationship traversals, immutable provenance,
image policy enforcement, authenticated administrative commands, atomic
batch publishing, idempotency and revision checks. Company adoption
currently caches identifiers for local operational search while retaining
`preferredCataloguePartId` and `referenceProvenance`; a platform
implementation should resolve references without duplicating entire
catalogue records.

See [INTRAFORGE_PLATFORM_REQUIREMENTS.md](INTRAFORGE_PLATFORM_REQUIREMENTS.md)
for the capability-by-capability acceptance criteria this mapping depends on.
